# 05 · 지금까지 배운 것

이 프로젝트에서 **실제로 틀렸던 것들**과 그것이 가르쳐 준 것입니다.
대부분 Claude가 만든 결함이고, 고친 커밋이 옆에 붙어 있습니다.
같은 실수를 두 번 하지 않기 위한 기록입니다.

---

## 물리 · 수치

### 정상상태로는 풀리지 않는다 (`ce630b9`)

2단계 첫 시도에서 8케이스 × 800반복이 **전부 continuity 잔차 7.5e-2에서
멈췄습니다.** 격자가 거칠어서가 아닙니다 — **엄밀 2차원 뭉툭한 물체 다발은
Re_max 1e4 이상에서 정상해가 존재하지 않습니다.** 2차원 후류는 Re ≈ 200
위에서 시간에 대해 주기적이고, 여기는 그 50~500배입니다. 상관식과 맞추려고
위·아래를 대칭면으로 둔 것이 스팬 방향 상관을 끊어 주는 효과까지 없앴습니다.

**교훈:** "수렴이 안 된다"를 먼저 격자 문제로 보지 말 것. 수렴할 대상이
존재하는지를 먼저 물을 것.

### 잔차 바닥은 미수렴이 아니다 (`7677d6b`)

비정상 해석의 내부 반복은 정상상태 기준에 닿도록 만든 것이 아닙니다.
continuity는 시간 스텝 안에서 압력-속도 결합이 버틸 수 있는 수준에서
**바닥**이 있습니다. 그런데 보고서는 그런 케이스를 "미수렴, GCI에서
제외했다"고 적었습니다 — **제외하지도 않았습니다.** 분석 코드는 넣고
있었고, 경고 문구만 별도 복사본을 갖고 있어서 바로 아래 표와 반대되는
말을 했습니다.

**교훈:** 같은 판정 규칙을 두 곳에 복사하면 두 곳이 어긋난다. 그리고 보고서가
분석에 대해 하는 진술은 분석 코드에서 나와야 한다.

### 진폭과 평균 이동은 다른 질문이다 (`7677d6b`)

정착한 와류열도 매 주기 자기 평균의 10%씩 흔들리고 **영원히** 그럽니다.
1% 기준을 peak-to-peak에 걸면 모든 비정상 케이스가 영원히 미수렴입니다.
멈춰야 하는 것은 **평균**입니다.

그런데 평균 이동을 재는 데 함정이 있습니다. 비교하는 두 블록이 **정수 개의
주기**를 담아야 합니다. 375샘플을 반으로 자르면 주기당 25샘플 기준으로
한쪽이 7.48주기가 되어 **없는 드리프트 0.8%를 만들어냅니다** — 찾으려는
1%와 같은 크기입니다. 반대로 실제 2% 상승은 위상 오차가 상쇄해서 놓칩니다
(0.15%로 나옴). 정수 주기로 자르면 정착 런은 0.03%, 인위적 x% 상승은
x%로 되읽힙니다.

**교훈:** 주기 신호의 통계를 낼 때는 창 길이가 주기의 정수배인지 확인할 것.
합성 신호로 검증할 것.

### 시계가 둘이다 — 시간 간격과 계산 길이 (`67f27b6`)

시간 간격은 와류 이탈 주기에서 잡았습니다 (맞음). **계산 길이도 같은
시계로** 잡았습니다 (틀림). 와류 주기는 봉 하나와 간극 속도가, 다발이
자리잡는 시간은 다발 길이와 벌크 속도가 정합니다.

캠페인 76케이스를 실제로 계산해 보니 "플러싱용 5주기"는 **다발 통과의
0.25~1.00회**였습니다. **한 케이스도 빠짐없이** 유동이 다발을 한 번
통과하기도 전에 평균을 시작했습니다.

**교훈:** 유도된 값은 유도한 근거가 맞는지 따로 확인할 것. 이건 코드를
다시 읽어서가 아니라 76케이스를 전부 숫자로 계산해 봐서 나왔습니다.

### 격자 사다리가 방향마다 다른 비율로 세밀해졌다 (`af39565`)

**이것이 2단계를 다시 설계하게 만든 결함입니다.**

격자 수렴 지수(GCI)는 **단일 세밀화 비**를 전제합니다 — 오차가 h 하나에
대해 h^p로 간다고 봅니다. 그런데 사다리의 실제 배율은:

| 방향 | 단계당 배율 |
|---|---|
| 원주 | ×1.46 |
| 유동 | ×1.45 |
| 반경 | ×1.20 |
| **벽면 수직** | **×1.00** |

`firstLayer`를 y+ = 1에 고정해 둔 탓에 **벽 근처 격자가 한 번도
세밀해지지 않았습니다.** 반경 셀 수가 1.2배씩 느는 것도 세밀화가 아니라
성장비 상한(1.45→1.12)을 조인 결과일 뿐이었습니다.

보고서의 h는 셀 면적 기준이라 **움직인 방향을 따라가는데**, Δp는 움직이지
않은 방향이 상당 부분 결정합니다. 관측 차수가 2.71 / 2.55 / **0.13**으로
나오고 마지막 삼중항 GCI가 **980%**가 된 이유입니다.

동시에, **원주 셀 수가 16~64개**였습니다 (L1은 셀당 22.5°). 그 해상도로는
박리점을 찍을 수 없고, Δp는 봉 표면 압력분포가 지배합니다. 격자를 세밀하게
할수록 Δp가 단조 감소하면서 **상관식 밴드를 관통해 아래로 나갔습니다**:

| | Eu_row |
|---|---|
| Gunter–Shaw | 0.405 |
| Žukauskas | 0.333 |
| Jakob | 0.318 |
| Shen 2024 | 0.255 |
| main-L1 (원주 16) | **0.466** ← 밴드 위 |
| main-L3 (원주 32) | 0.295 ← 밴드 안 |
| main-L5 (원주 64) | **0.227** ← 밴드 아래 |
| Richardson 외삽 | **0.208** |

수렴 중인 것이 아니라 **점근 영역에 들어가지도 못한** 상태였습니다.

**교훈:** 격자 사다리를 자동 규칙에 맡기면, 규칙이 각 방향을 독립적으로
다루면서 GCI의 전제를 조용히 깬다. **모든 방향을 같은 비율로 — 첫 층
포함해서.** y+ < 1은 해롭지 않으므로 첫 층도 같이 줄이면 된다.
→ 그래서 지금은 [격자를 사람이 지정합니다](02-격자-직접-지정.md).

### 상관식 밴드는 ±20%가 아니다 (`3cd585e`)

두 개만 비교했을 때 "±20% 이내"라고 적었는데, Gunter–Shaw를 넣으니
**1.0~2.2배(보통 1.45배)**로 넓어졌습니다. 주장을 철회하고 밴드를
데이터에서 계산하도록 바꿨습니다.

**교훈:** "대략 몇 % 이내"를 두 개로 말하지 말 것. 계산해서 말할 것.

## 도구 · 코드

### 정적 settings 트리는 릴리스에 대한 주장이지 설치본에 대한 사실이 아니다 (`1355f1b`)

`setup.general.solver.time = 'transient'`가 배포된 2026 R1 트리에는
허용값으로 **있습니다.** 실제 2026 R1은 거부하고 다른 네 값을 알려줍니다.
감사(audit)는 초록이었고 계산은 61초에 죽었습니다.

지금은 실행 중인 세션에 `allowed_values()`를 물어보고, 안 알려주면 후보를
순서대로 시도하고, 채택된 값을 기록합니다.

**교훈:** 오프라인 검증에는 한계가 있다. "확인했다"의 범위를 정확히 알 것.

### 모니터가 계산보다 비쌌다 — 두 번 (`fe01d05`, `0fe806d`)

gRPC 왕복 한 번이 약 0.2초입니다. 처음에는 매 반복마다 잔차 이력을 읽어서
케이스당 210초 중 **173초가 모니터링**이었습니다. 고친 뒤, 비정상으로
바꾸면서 **같은 버그가 다른 콜백에 다시** 생겼습니다 — 스텝당 왕복 5회 ×
500스텝 = 케이스당 9분.

두 번 다 **로그의 타이밍 두 줄을 분해해서** 찾았습니다 (13,504셀 →
209.8초, 24,576셀 → 240.2초 ⇒ 셀당 비용과 반복당 고정비용을 분리).

**교훈:** 콜백 안에 든 것은 호출 횟수만큼 곱해진다. 그리고 한 번 고친
버그는 다른 곳에 다시 생긴다.

### 스모크 테스트 없이 캠페인을 돌렸다 (`275ba2d`)

55분과 8케이스를 써서, 1번 케이스가 3분 만에 알려줄 수 있었던 것을
배웠습니다. 지금은 1번 케이스가 쓸 수 있는 해를 내지 못하면 **거기서
멈춥니다.**

**교훈:** 긴 배치는 첫 하나로 판정하고 멈출 수 있어야 한다.

### 미수렴 해로 GCI를 만들었다 (`275ba2d`)

관측 차수 1.95 / 1.48 / 3.21, GCI 6.2% — **전부 의미 없는 숫자**였는데
답처럼 보였습니다. 수치를 명시적으로 철회했습니다. 지금은 미수렴 행을
표에는 남기고 모든 외삽에서 빼며, 수렴한 것이 3개 미만이면 GCI를 만들지
않고 빨간 글씨로 그 이유를 적습니다.

**교훈:** 절차가 입력을 검증하지 않으면, 답처럼 생긴 것을 만들어 낸다.

### 이력이 프로세스 메모리에만 있었다 (`c20e7f7`, `eb44f36`)

버그를 고치려고 서버를 다시 켰더니 **그 버그의 증거가 사라졌습니다.**
지금은 잔차·Δp 이력이 `results.json`에 들어갑니다. Δp는 상한 2000점으로
500스텝 런을 통째로 저장합니다 — 진동을 비정수 간격으로 솎으면
엘리어싱되므로 솎지 않습니다.

**교훈:** 진단에 필요한 것은 디스크에 있어야 한다.

### 정의 파일이 결과를 덮어썼다 (`67f27b6`)

`--make`와 탭의 재생성이 **이미 결과가 있는 `study.json`을 말없이
덮어썼습니다.** 그러면 실행되지 않은 런을 기술하는 정의가 실제 결과 옆에
놓이고, 남은 케이스는 기록된 케이스와 다르게 돌아갑니다. 어느 쪽도 그
자체로는 틀리지 않은데 **섞인 게 틀렸고 표에는 표시가 안 납니다.**

지금은 결과가 있으면 저장을 거부하고, 각 결과 행이 **실제로 돌아간
제어값**을 기록하며, 정의가 바뀐 연구를 이어서 돌리려 하면 거부합니다.

**교훈:** 정의와 결과는 하나의 객체다. 한쪽만 바꿀 수 있으면 안 된다.

### 빌드 산출물을 git에 넣었다 (`8ea91b2`)

`report.html`이 커밋돼 있는데 앱이 버튼을 누르면 그 파일을 새로 씁니다.
그래서 버튼을 누른 사람은 `git pull`이 막힙니다. **앱을 정상적으로 쓰면
막히는** 구조였습니다.

**교훈:** 버튼 한 번으로 재생성되는 파일은 커밋하지 않는다. 정의와 측정값만.

### 케이스당 코어를 바꿀 수 없었다 (`b915e92`)

`Runner.__init__`에 "**the way to use the machine is more CASES, not more
cores per case**"라는 주석을 직접 써 놓고, 캠페인에서 그걸 실행할 방법이
없었습니다. 어떤 연구도 `launch` 그룹을 설정하지 않으니 전부 스키마 기본값
4코어를 가져갔고, 어느 패널에서도 바꿀 수 없었습니다.

게다가 4코어는 이 격자들에 틀린 숫자였습니다 — 랭크당 3,376~44,032셀,
전부 손익분기(약 5만) 아래. **케이스 하나를 느리게 만들면서 한 개씩**
돌리고 있었습니다.

**교훈:** 주석으로 쓴 원칙이 코드로 실행 가능한지 확인할 것.

### 배너가 헤더 위로 날아갔다 (`c20e7f7` 무렵)

`.banner.warn`이 형상 탭 툴팁의 `.warn`에서 `position:absolute;
display:none`을 상속했습니다. Fluent 없는 세션마다 세팅 배너가 헤더 위로
날아가고 있었습니다.

**교훈:** 클래스 이름 재사용은 CSS에서 조용히 상속을 물려준다.

### 검사 코드가 세 번째 사본이었다 (`--check`)

브라우저의 공식을 검사한다는 코드가 **같은 공식의 세 번째 사본**이었습니다.
페이지가 다른 말을 하는데도 통과할 수 있었습니다. 지금은 HTML에서
`gapVelocity`/`lossModel`을 중괄호 매칭으로 뽑아내 node에서 실제로
실행합니다.

**교훈:** 검사는 대상을 실행해야 한다. 다시 구현하면 검사가 아니다.

### 테스트끼리 경쟁했다

브라우저 스위트 두 개를 같은 서버에 돌리면 `studies/`를 공유해서 엉뚱한
실패가 났습니다. 또 여러 서버를 띄워 두면 하나가 끝난 연구에 결과를 계속
쓰고 있었습니다.

**교훈:** 공유 상태를 쓰는 테스트는 직렬로, 깨끗한 서버에서.
